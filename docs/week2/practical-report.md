# Practical 2 Report

## Requirements Interviews and Formal User Stories

## 1. Objective

The objective of Practical 2 was to obtain target-user feedback about the proposed Reading Compass application and convert the resulting requirements into formal, prioritised and estimated user stories.

## 2. Team

- **Tianyang Zhang:** Lead Developer and Technical Lead
- **Yuhao Guo:** Project Coordinator and Requirements, Documentation and QA Lead

## 3. Task One - Target-User Interviews

The team conducted in-person interviews with potential Reading Compass users.
The available notes do not record names, interview dates or the participant
count. For that reason, the report uses a combined summary and does not claim
individual quotations.

The interviews explored:

- Existing approaches to organising books
- Problems with current reading-tracking methods
- Preferred progress-tracking methods
- The value of reading plans, notes and reflections
- Search and filtering requirements
- Usability and privacy expectations

The complete consolidated findings are documented in [Target-User Interview Findings](interview-findings.md).

## 4. Main Findings

The interviews confirmed a need for a focused personal reading application. The most important findings were:

- Users currently store reading information across notes, spreadsheets, screenshots and informal lists.
- Users want a central personal reading list.
- Reading progress should be quick to update.
- Completion targets should be optional.
- Search and status filtering become important as reading lists grow.
- Notes, reflections and reading activity should remain private.
- The interface should use simple navigation and minimise required fields.
- Duplicate-book warnings would improve the quality of stored information.

## 5. Task Two - Formal User Stories

The interview findings were converted into ten formal user stories. Each requirement includes:

- A title
- A short description
- A user story
- A priority using the 10/20/30/40/50 scale
- An effort estimate in development days
- A rationale for the selected priority

The complete set is documented in the [Requirements Backlog](requirements-backlog.md).

## 6. Priority Interpretation

For this project, lower numbers represent higher priority:

- **10:** Essential
- **20:** High
- **30:** Medium
- **40:** Low
- **50:** Optional

This scale supports implementation planning by separating the minimum usable product from lower-priority enhancements.

## 8. Backlog Refinements

Compared with the initial Week 1 backlog:

- Target completion dates were clarified as optional.
- Progress tracking was defined using current page and calculated percentage.
- Notes and completion reflections were clarified as private.
- Search was defined for both title and author.
- Status filtering was made explicit.
- Duplicate-book warning was added.
- Formal descriptions, priorities, estimates and rationales were added.
